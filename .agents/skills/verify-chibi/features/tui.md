# Terminal UI

`chibi run --tui` runs the node in-process under a terminal UI while JSON-RPC keeps serving the wallet. Before the node starts it asks for the password of the user's keystore (`--keystore` or the config's `keystore`), or, with neither, opens setup screens that create a wallet from a new recovery phrase, import a private key or phrase, or take an existing keystore path, and it watches the decrypted address. A dozing cat shows the wait for a state peer with live peer counts, perks up at `found a state peer!`, and then a transfer form sends ETH or a registry token the address holds: validated per field, reviewed, signed, broadcast through chibi, and tracked to a verified receipt. Sending works only while a state peer is connected and only on Sepolia.

## Sub-features

- `tui-flags` `--tui` takes every `run` flag; `--tui` with `-b` and `--logs` without `--tui` are refused by the parser; `chibi init --keystore PATH` writes `keystore`; a relative `keystore` in the config fails as not absolute; `--keystore` naming a missing file fails with `cannot read the keystore <path>`.
- `tui-setup-menu` with no keystore named, the UI opens `no keystore yet: set up the wallet to send from` with `create a new wallet`, `import a private key or recovery phrase`, and `use an existing keystore file`; Up/Down move the `>` marker, Enter selects, Esc on the menu quits before the node starts, and Esc on any later setup step returns to the menu.
- `tui-setup-create` the 12 words numbered `1.` to `12.` with `write these words down. anyone with them controls this wallet. chibi will not show them again.`; Enter asks `confirm your recovery phrase: enter words N and M`, one masked `word N` at a time; a wrong word shows `that is not word N; check what you wrote down` and asks again; Esc on the words or the confirmation returns to the menu and a new Create shows different words.
- `tui-setup-import` one masked `secret` field; 64 hex digits (with or without `0x`) are a key, 12 or 24 words a phrase; `expected a private key (64 hex digits) or a recovery phrase (12 or 24 words)`, `a recovery phrase has 12 or 24 words; this has N`, `word N is not in the English BIP-39 word list`, and `the recovery phrase's checksum does not match; check the words and their order` for what is neither; the Anvil phrase `test test test test test test test test test test test junk` gives `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`.
- `tui-setup-password` two masked fields; `a password needs at least 8 characters`; `the passwords do not match; enter them again`.
- `tui-setup-save` the keystore lands at `<config dir>/keystores/<checksummed address>.json` (dir 0700, file 0600) and decrypts with the password; the footer says `saved the keystore for <address> to <path>` and the dozing cat follows without another password prompt; the config gains `keystore = "<path>"` keeping its other keys, or is created with the defaults plus `keystore`; the next run goes straight to the password prompt; saving the same address again says `a keystore for <address> is already at <path> and was not overwritten; enter its password` and leaves the file unchanged.
- `tui-setup-existing` a path field (absolute or `~/`); `no file at <path>` for a missing file, `enter an absolute path, or one starting with ~/` for a relative one; a real file goes to the password prompt.
- `tui-unlock` a masked password prompt; a wrong password re-asks with `wrong password, try again`; a missing or unreadable keystore exits before anything starts with `cannot read the keystore <path>`; Esc quits before the node starts. Keystores written by `cast` and by geth (with an `address` field) both unlock.
- `tui-waiting` the dozing cat above `looking for a state peer · peers N · state peers M · <elapsed>`, updated at least once a second; then `found a state peer!` for at least 1.5 s, even when anchoring is faster, and until anchored.
- `tui-cats` with `COLORTERM=truecolor` the cats are half-block (`▀`, `▄`) pixel art in 24-bit colour, 22 columns by 8 rows, animated every 250 ms: Waiting a closed-eyed cat bobbing with a 4x4 Z drifting up to its right; Excited a wide-eyed cat hopping with stars swapping between the top-left and lower-right corners and the top-right and lower-left; Paused a cat nodding with closed and half-open eyes; a verified status-1 receipt a cat with `^`-shaped eyes bouncing under a rising heart; the form, on a terminal at least 70 columns wide and only where it fits beside the form's widest row (the token row's proving hint widens it to about 80 columns), a 16-column cat right of the form, blinking about every 3 s, and none otherwise. The form's text stays where it is without the cat. With `COLORTERM` unset or `NO_COLOR` set, the ASCII cats (`( -.- )`, `( ^o^ )`, `( u.u )`, `( ^.^ )`) show instead and nothing sits beside the form.
- `tui-form` `from` (checksummed address and ETH balance), `token` (ETH and held registry tokens, left/right; until every pinned key is held the row adds a dim `more tokens appear once their balances are proven`), `amount` (decimal or `max`), `to`, and `fee` (max fee, gas, and gwei, refreshed each head; a revert shows its reason).
- `tui-validate` per-field messages that keep the input: `refusing to send to the zero address`, `the checksum does not match; check the address, or type it all lowercase`, `expected 0x followed by 40 hex digits`, `<SYMBOL> has at most <N> decimals`, `more than your balance of ...`, `the amount plus the max fee ... is more than your balance of ...`, `waiting for the fee estimate`; for `max` ETH the fee row says `your balance of ... does not cover the max fee ...` or `the fee keeps changing what max sends; enter an exact amount instead`.
- `tui-send` Review shows `sepolia (chain id 11155111)`, the full recipient, exact amount, and max fee (for `max` ETH, the fee estimated with the amount shown); `y` signs an EIP-1559 transaction and submits it; the screen goes from the hash and `pending` to `included in a block; verifying the receipt...` to `sent! the receipt is verified with status 1` with a happy cat; `still pending after N blocks` after 10 heads; a transfer whose nonce another transaction took shows `this transfer was replaced or dropped: its nonce was used by another transaction` and quits without the outbox warning.
- `tui-paused` with no state peer connected, a sleepy cat and `waiting for a state peer`; Enter does nothing; the form returns unchanged when one connects. Leaving the Sending screen with no state peer lands on Paused, and signing re-checks the state peer count and refuses with `not sent: waiting for a state peer`.
- `tui-mainnet` on mainnet the form shows balances and Review says `sending on mainnet is not enabled yet`; `y` signs nothing.
- `tui-keys` `l` toggles the log pane (the last log lines; nothing is printed to the terminal), `q` or Ctrl-C quits and stops the node as SIGINT does; with a transfer pending the first `q` warns that chibi's outbox rebroadcasts it on the next run.

## How to get to it (user POV)

- With no keystore, run `chibi run --tui` and follow the setup screens: create a wallet (write the 12 words down and type back the two asked), import a private key or recovery phrase, or name a keystore file. Or import a key once with `cast wallet import <name> --interactive`, then `chibi init --keystore ~/.foundry/keystores/<name>` or pass `--keystore` to `chibi run --tui`.
- Run `chibi run --tui` (add `--logs` to start with the log pane open), type the password, wait for the cat, then fill the form and press Enter, then `y`.
- Point the wallet at the same URL as with `chibi run`; it keeps working while the TUI runs.

## Driving it with verify-chibi scripts

Preconditions:

- `launch.sh` does not apply: it starts a plain `chibi run`. Drive the TUI in tmux from a scratch HOME instead: `S=$(mktemp -d /tmp/chibi-tui.XXXX); mkdir -p "$S/evidence" "$S/ks"`, `E="env -u CHIBI_CONFIG -u NO_COLOR COLORTERM=truecolor HOME=$S XDG_CONFIG_HOME=$S/.config XDG_DATA_HOME=$S/.local/share"`, and `B=$PWD/target/release/chibi` after `cargo build --release -p chibi`.
- A free scratch port, for example 8750: `lsof -nP -iTCP:8750 -sTCP:LISTEN` prints nothing. Never use 8545 or 8546, and never the user's keystore.
- A scratch keystore: `cast wallet new "$S/ks" --unsafe-password hunter2` (unfunded; enough for every sub-feature but `tui-send`). For `tui-send`, a funded Sepolia key in `CHIBI_VERIFY_KEY` imported as `cast wallet import funded --private-key "$CHIBI_VERIFY_KEY" --unsafe-password hunter2 --keystore-dir "$S/ks"`; without it report `tui-send` as skipped for that reason. `KS` is the keystore file in `$S/ks`.
- `tmux`, `cast`, and outbound Sepolia access as in the [baseline](./README.md#baseline-preconditions).

- **Flags.** `$E $B run --tui --rpc-port 8750 --keystore "$S/ks/missing"` exits non-zero with `cannot read the keystore $S/ks/missing` and opens no port. `$E $B run --tui -b` and `$E $B run --logs` exit 2 with a usage error. `$E $B init --network sepolia --rpc-host 127.0.0.1 --rpc-port 8750 --keystore "$KS" </dev/null` writes `keystore = "<KS>"` into `$S/.config/chibi/config.toml`, so later runs need no `--keystore`. A config with `keystore = "rel.json"` fails with `keystore rel.json is not an absolute path`.
- **Setup.** Use a second scratch HOME with no config, so nothing names a keystore: `T=$(mktemp -d /tmp/chibi-setup.XXXX)`, `F="env -u CHIBI_CONFIG HOME=$T XDG_CONFIG_HOME=$T/.config XDG_DATA_HOME=$T/.local/share"`. Run `tmux new-session -d -s chibi-setup -x 200 -y 40 "$F $B run --tui --rpc-port 8751 --logs; echo exit=\$?; sleep 600"` (wide, so the saved path fits the footer). The pane shows the menu with `> create a new wallet`. Press Enter: the pane shows 12 numbered words and the backup warning; read them with `tmux capture-pane -p -t chibi-setup | grep -oE '[0-9]+\. [a-z]+'` into a scratch shell variable, never into evidence. Press Enter: the pane shows `confirm your recovery phrase: enter words N and M`. Type a wrong word with `tmux send-keys -t chibi-setup -l zzz`, then `send-keys Enter`: `that is not word N; check what you wrote down`. Type word N, Enter, then word M, Enter (each with `send-keys -l`, Enter separately). On the password screen type `short` + Enter (`a password needs at least 8 characters`), then `hunter22` + Enter and `hunter23` + Enter (`the passwords do not match; enter them again`), then `hunter22` + Enter twice. Within a few seconds the footer shows `saved the keystore for 0x... to $T/.config/chibi/keystores/0x....json` above the dozing cat, with no password prompt. `stat -c '%a %n' "$T/.config/chibi/keystores" "$T"/.config/chibi/keystores/*.json` prints `700` and `600`; `cast wallet address --keystore <that file> --password hunter22` prints the address in the header; `$T/.config/chibi/config.toml` holds `keystore = "<that file>"`. Quit with `q`, run `tmux kill-session -t chibi-setup`, and rerun the same tmux command (every rerun below kills the session first): it opens `unlock your keystore to send from it` directly. Quit with Esc.
- **Import.** In `$T/.config/chibi/config.toml`, which setup wrote with the defaults, remove the `keystore` line and change `rpc_port = 8545` to `rpc_port = 8751`. Run the tmux command again, press Down and Enter, type `tmux send-keys -t chibi-setup -l 'test test test'`, Enter: `a recovery phrase has 12 or 24 words; this has 3`. Then `send-keys -l 'test test test test test test test test test test test junk'`, Enter, and `hunter22` twice: the header and footer show `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266` and the keystore `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266.json`, and the config still has `rpc_port = 8751` alongside `keystore`. Quit, remove the `keystore` line again, and import the Anvil key `0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80` (with `send-keys -l`): the footer says `a keystore for 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266 is already at ... and was not overwritten; enter its password`, and `hunter22` unlocks it. The Anvil account is public; never import a real key this way in a shared tmux.
- **Existing.** Remove the `keystore` line, run again, press Up and Enter, type `send-keys -l "$T/missing.json"`, Enter: `no file at $T/missing.json`. Clear it with `BSpace`s, type `send-keys -l "$KS"`, Enter: the password prompt; `hunter2` unlocks it.
- **Unlock.** Run `tmux new-session -d -s chibi-tui -x 120 -y 40 "$E $B run --tui --rpc-port 8750 --logs; echo exit=\$?; sleep 600"`. `tmux capture-pane -p -t chibi-tui` shows `unlock your keystore to send from it` and `password`. Run `tmux send-keys -t chibi-tui 'wrong' Enter`; within a few seconds the pane shows `wrong password, try again`. Run `tmux send-keys -t chibi-tui 'hunter2' Enter`.
- **Waiting.** Capture the pane twice a few seconds apart: the half-block cat sits above `looking for a state peer · peers N · state peers 0 · <elapsed>`, and the elapsed time moves. Capture it twice more 250 ms apart (`tmux capture-pane -p -t chibi-tui > a; sleep 0.25; tmux capture-pane -p -t chibi-tui > b; diff a b`): the cat's rows differ, since the z moves every frame. `tmux capture-pane -p -e` shows the colours as `38;2;59;42;32` (the outline) escapes. The log pane shows `waiting for a state peer (snap/2)` and the `starting` line with `watched=1`, the keystore's address.
  The counts and elapsed time start once the light client has synced; until then the line reads `peers 0 · state peers 0 · 0s`.
- **Serving.** When a state peer connects the pane shows `found a state peer!` (capture it: it stays up at least 1.5 s), then the form with `from <checksummed address>` and its ETH balance. The balance shows within a few seconds of the form as the address's proofs arrive, without waiting for the next head; `? ETH` past that is a regression. The token row shows `more tokens appear once their balances are proven` until the registry tokens' balances are proven, then drops it; seeding starts when the node serves, not at the next head, so it usually drops before the first new head. In another shell, `cast chain-id --rpc-url http://127.0.0.1:8750` prints `11155111` and `cast balance <address> --rpc-url http://127.0.0.1:8750` matches the form's balance at that head.
- **Validate.** On the form, type `1`, press Down, run `tmux send-keys -t chibi-tui -l 0x0000000000000000000000000000000000000000`, press Enter: the pane shows `refusing to send to the zero address` and both inputs stay. Clear the recipient with `BSpace`, run `tmux send-keys -t chibi-tui -l 0x7f02C3E3c98b133055B8B348B2Ac625669Ed295d` (last letter case flipped), press Enter: `the checksum does not match; check the address, or type it all lowercase`. With the unfunded keystore and a valid recipient, Enter shows `more than your balance of 0.00 ETH`.
- **Send.** With the funded keystore, set amount `0.000000001` and `to` an address you control (typed with `send-keys -l`), wait for the `fee` row to show `... ETH (<gas> gas at up to <gwei> gwei)`, press Enter. Review shows `sepolia (chain id 11155111)`, the checksummed recipient, `0.000000001 ETH`, and the max fee. Press `y`. The pane shows `hash 0x...`, then `pending`, then `sent! the receipt is verified with status 1` under the bouncing half-block cat and its heart. Then `cast receipt <hash> --rpc-url https://ethereum-sepolia-rpc.publicnode.com` shows `status 1` in the same block, and `cast receipt <hash> --rpc-url http://127.0.0.1:8750` agrees (chibi serves receipts for transactions it submitted).
- **Cats.** On the form in the 120-column session, the pane shows the half-block cat right of the form's rows, not overlapping them; `tmux resize-window -t chibi-tui -x 60` removes it, and `-x 120` brings it back. For the ASCII fallback, quit and run the Unlock command again with `$E env -u COLORTERM $B ...` in place of `$E $B ...`: the waiting screen shows `( -.- )` or `( o.- )`, the form shows no cat, and `capture-pane -p` contains no `▀` or `▄`. Run it once more with `$E env NO_COLOR=1 $B ...`: the same.
- **Quit.** Press `q`; with a transfer still pending the pane first shows `a transfer is still pending; chibi's outbox rebroadcasts it on the next run. press q again to quit`, and a second `q` quits. The pane then shows `exit=0` on a normal screen (raw mode and the alternate screen restored), and `lsof -nP -iTCP:8750 -sTCP:LISTEN` prints nothing.
- **Mainnet.** Optional and slow (mainnet has no known state peers): run the TUI with `--network mainnet`; once the form opens, a valid transfer's Review says `sending on mainnet is not enabled yet` and `y` changes nothing.
- **Proof.** Before quitting each stage, `tmux capture-pane -p -t chibi-tui > "$S/evidence/<stage>.txt"`, with the log pane open (`l`) where the log matters. Keep the `cast` outputs next to them. Never capture the password, the private key, or the backup screen's words; capture setup panes only on the menu, confirmation, password, and saved screens.
- **Cleanup.** `tmux kill-session -t chibi-tui` and `tmux kill-session -t chibi-setup`, then remove `$S` except `$S/evidence`, and all of `$T`.

## Gotchas

- There is no `chibi.log`: under `--tui` the log goes to an in-memory buffer of the last 1000 lines, shown only in the log pane, and it is gone when the TUI exits. Capture the pane with the log pane open for node proof.
- Decrypting a `cast` keystore takes a second or two (scrypt); the prompt shows `unlocking...` meanwhile.
- `Paused` appears only when every state peer drops after serving, which cannot be forced reliably on Sepolia; report `tui-paused` as observed or as not driven, never as verified from unit tests.
- The fee row and `max` for ETH need a finished estimate; Enter before it shows `waiting for the fee estimate`.
- The `to` field accepts only hex digits and `x`, and `amount` only digits, `.`, and the letters of `max`, so `q` and `l` always act as keys.
- A transfer left pending stays in the scratch data directory's outbox; a later `chibi run` on the same data directory broadcasts it again.
- `tmux send-keys` reads an argument that starts with `0x` as a hex key code, not as text, so `send-keys -t chibi-tui 0xabc...` types the wrong thing. Type addresses with `send-keys -l` (literal), and send Enter in a separate `send-keys` call.
- The password is at most 256 bytes; longer input is ignored.
- The setup screens take every printable key as typing, so `q` and `l` type rather than quit or open the log pane; Esc goes back to the menu and Esc on the menu quits.
- The words stay on the backup screen only until the next key; capture them before pressing Enter.
- Some frames differ only in colour, such as the form cat's blink (eye pixels turn from dark to orange under the same `▀`). A plain `capture-pane -p` cannot see that; compare `capture-pane -p -e` captures, which keep the colour escapes.
