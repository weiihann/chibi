# Terminal UI

`chibi wallet` runs the node in-process under a terminal UI while JSON-RPC keeps serving the wallet. Before the node starts it asks for the password of the user's keystore (`--keystore` or the config's `keystore`), or, with neither, opens setup screens that create a wallet from a new recovery phrase, import a private key or phrase, or take an existing keystore path, and it watches the decrypted address. A dozing cat shows the wait for a state peer with live peer counts, perks up at `found a state peer!`, and then a transfer form sends ETH or a registry token the address holds to an address or an ENS name: validated per field, reviewed, signed, broadcast through chibi, and tracked to a verified receipt. Sending works only while a state peer is connected and only on Sepolia.

## Sub-features

- `tui-flags` `chibi wallet` takes every `chibi node` flag but `-b`; `chibi wallet -b`, `chibi node --logs`, and `chibi run` are refused by the parser; `chibi init --keystore PATH` writes `keystore`; a relative `keystore` in the config fails as not absolute; `--keystore` naming a missing file fails with `cannot read the keystore <path>`.
- `tui-setup-menu` with no keystore named, the UI opens `no keystore yet: set up the wallet to send from` with `create a new wallet`, `import a private key or recovery phrase`, `use an existing keystore file`, and `just watch balances, without a wallet`; the `>` starts on `create a new wallet`, or on the watch choice when the run watches an address (config `addresses`); Up/Down move the `>` marker and wrap, Enter selects, Esc on the menu quits before the node starts, and Esc on any later setup step returns to the menu.
- `tui-setup-create` the 12 words numbered `1.` to `12.` with `write these words down. anyone with them controls this wallet. chibi will not show them again.`; Enter asks `confirm your recovery phrase: enter words N and M`, one masked `word N` at a time; a wrong word shows `that is not word N; check what you wrote down` and asks again; Esc on the words or the confirmation returns to the menu and a new Create shows different words.
- `tui-setup-import` one masked `secret` field; 64 hex digits (with or without `0x`) are a key, 12 or 24 words a phrase; `expected a private key (64 hex digits) or a recovery phrase (12 or 24 words)`, `a recovery phrase has 12 or 24 words; this has N`, `word N is not in the English BIP-39 word list`, and `the recovery phrase's checksum does not match; check the words and their order` for what is neither; the Anvil phrase `test test test test test test test test test test test junk` gives `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`.
- `tui-setup-password` two masked fields; `a password needs at least 8 characters`; `the passwords do not match; enter them again`.
- `tui-setup-save` the keystore lands at `<config dir>/keystores/<checksummed address>.json` (dir 0700, file 0600) and decrypts with the password; the footer says `saved the keystore for <address> to <path>` and the dozing cat follows without another password prompt; the config gains `keystore = "<path>"` keeping its other keys, or is created with the defaults plus `keystore`; the next run goes straight to the password prompt; saving the same address again says `a keystore for <address> is already at <path> and was not overwritten; enter its password` and leaves the file unchanged.
- `tui-setup-existing` a path field (absolute or `~/`); `no file at <path>` for a missing file, `enter an absolute path, or one starting with ~/` for a relative one; a real file goes to the password prompt.
- `tui-unlock` a masked password prompt with the footer `Enter unlock · Tab watch only · Esc quit`; a wrong password re-asks with `wrong password, try again`; a missing or unreadable keystore exits before anything starts with `cannot read the keystore <path>`; Esc quits before the node starts; Tab leaves without unlocking, wipes the typed password, and watches as in `tui-watch` (the address prompt first when nothing is watched, whose Esc returns to the password prompt). Keystores written by `cast` and by geth (with an `address` field) both unlock.
- `tui-watch` choosing to watch with an address watched starts the node at once; with none, `the address to watch` takes `0x` and 40 hex digits, refusing with `enter the address to watch`, `enter the address; names resolve only once the node runs`, `expected 0x followed by 40 hex digits`, `the checksum does not match; check the address, or type it all lowercase`, and `refusing to watch the zero address`, keeping the input; Esc returns to the menu. A valid address joins the run's watch list and the config's `addresses` (created with the defaults when missing, other keys and the `keystore` line kept, no duplicate); with a read-only config it is watched anyway and the notice says `watching <address> for this run; could not add it to <config>: <reason>. add "<address>" to addresses in that file to keep watching it`. After the dozing and found screens, the box is titled `chibi · <network> · watching` and lists each watched address once, in config order, as the checksummed address, its primary name if any, its ETH balance, and each held registry token, with `more tokens appear once their balances are proven` until they are; the footer is `l logs · q quit`; a list taller than the body scrolls by address with Up/Down, between the first address and only the last, with a dim `↑ N more` on the top row and `↓ N more` under the list counting the addresses out of view, and the footer `up/down scroll · l logs · q quit` while any is; no form, fee, resolution, or send; the paused cat stands in while no state peer is connected; on a terminal of at least 78 columns the idle cat sits beside the list where it fits.
- `tui-waiting` the dozing cat above `looking for a state peer · peers N · state peers M · <elapsed>`, updated at least once a second; then `found a state peer!` for at least 1.5 s, even when anchoring is faster, and until anchored.
- `tui-cats` with `COLORTERM=truecolor` the cats are half-block (`▀`, `▄`) pixel art in 24-bit colour, 22 columns by 8 rows at their own size and 44 by 16 at twice it (see `tui-layout`), animated every 250 ms: Waiting a closed-eyed cat bobbing with a 4x4 Z drifting up to its right; Excited a wide-eyed cat hopping with stars swapping between the top-left and lower-right corners and the top-right and lower-left; Paused a cat nodding with closed and half-open eyes; a verified status-1 receipt a cat with `^`-shaped eyes bouncing under a rising heart; the form, when its body is at least 70 columns wide (a terminal of at least 78) and only where it fits beside the form's widest row (a row too wide for the body continues under its values, see `tui-form`), a cat right of the form, 32 columns wide where that fits across and down and 16 otherwise, blinking about every 3 s, and none otherwise or while the token list is open. The form's text stays where it is without the cat. With `COLORTERM` unset or `NO_COLOR` set, the ASCII cats (`( -.- )`, `( ^o^ )`, `( u.u )`, `( ^.^ )`) show instead and nothing sits beside the form.
- `tui-layout` on a terminal of at least 44x14 the UI is a rounded box (`╭`, `╮`, `╰`, `╯`) centered in the terminal with `chibi · <network> · <address>` in its top border (`chibi · <network> · <name> · <address>` when the address has a primary name that prints as itself), `min(columns - 4, 120)` wide and `min(rows - 2, 36)` tall, or `min(rows - 2, 48)` with the log pane open, the footer on its last inner rows (its keys packed into as many rows as the width needs, ` · ` between them and none split: two rows on the form at 80x24, one at 120x40) and nothing outside it; the waiting, found, paused, and receipt screens center the cat, a blank row, and the centered lines in the box; the pixel cat is 44x16 cells when the body inside the box is at least 88 columns by 32 rows (a 120x40 or 200x60 terminal with the log pane closed) and 22x8 otherwise (80x24, or 120x40 with the log pane open); the text stays the terminal's font size; below 44x14 the borderless layout fills the terminal with the header on the first row and the footer on the last rows.
- `tui-form` `from` (checksummed address and ETH balance), `token` (ETH and held registry tokens; focused, the row adds a dim `Enter to choose`, and Enter opens a `choose a token` list below it with each token's symbol, name (`Ether` for ETH) and balance, a `>` on the current one, a filter typed on symbol or name (`no token matches` when none does), and `type to filter · Enter pick · Esc cancel` on its bottom border; left/right still cycle; until every pinned key is held the row and the list add a dim `more tokens appear once their balances are proven`), `amount` (decimal or `max`), `to` (an address or an ENS name; under a name a dim `resolving...`, then a dim `→ <checksummed address>`, or in red `<name> has no address`, `<name> is not registered`, `<name> is served offchain, which chibi does not follow`, or `could not resolve <name>: <reason>`), and `fee` (max fee, gas, and gwei, refreshed each head; a revert shows its reason). A row too wide for the box continues on the next line at the value column, 10 columns in, breaking only between the address, the balance, and each hint, never inside one: at 80x24 an 18-decimal ETH balance sits under the `from` address, and the token list opens below the token row's last line.
- `tui-validate` per-field messages that keep the input: `refusing to send to the zero address`, `the checksum does not match; check the address, or type it all lowercase`, `expected 0x followed by 40 hex digits`, `expected 0x followed by 40 hex digits, or a name like name.eth`, `chibi takes names in plain letters, digits and hyphens; paste the address for others`, `waiting for <name> to resolve`, `<SYMBOL> has at most <N> decimals`, `more than your balance of ...`, `the amount plus the max fee ... is more than your balance of ...`, `waiting for the fee estimate`; for `max` ETH the fee row says `your balance of ... does not cover the max fee ...` or `the fee keeps changing what max sends; enter an exact amount instead`.
- `tui-send` Review shows `sepolia (chain id 11155111)`, the full recipient (for a name, the name and under it the checksummed address it resolved to, which is what is signed), exact amount, and max fee (for `max` ETH, the fee estimated with the amount shown); `y` signs an EIP-1559 transaction and submits it; the screen goes from the hash and `pending` to `included in a block; verifying the receipt...` to `sent! the receipt is verified with status 1` with a happy cat; `still pending after N blocks` after 10 heads; a transfer whose nonce another transaction took shows `this transfer was replaced or dropped: its nonce was used by another transaction` and quits without the outbox warning.
- `tui-paused` with no state peer connected, a sleepy cat and `waiting for a state peer`; Enter does nothing; the form returns unchanged when one connects. Leaving the Sending screen with no state peer lands on Paused, and signing re-checks the state peer count and refuses with `not sent: waiting for a state peer`.
- `tui-mainnet` on mainnet the form shows balances and Review says `sending on mainnet is not enabled yet`; `y` signs nothing.
- `tui-keys` `l` toggles the log pane (the last log lines; nothing is printed to the terminal), `q` or Ctrl-C quits and stops the node as SIGINT does; on the `to` field `q` and `l` type into it, Ctrl-C still quits, and the footer says `Ctrl-C quit` without `l logs`; with a transfer pending the first `q` warns that chibi's outbox rebroadcasts it on the next run.

## How to get to it (user POV)

- With no keystore, run `chibi wallet` and follow the setup screens: create a wallet (write the 12 words down and type back the two asked), import a private key or recovery phrase, name a keystore file, or just watch balances. Or import a key once with `cast wallet import <name> --interactive`, then `chibi init --keystore ~/.foundry/keystores/<name>` or pass `--keystore` to `chibi wallet`.
- Run `chibi wallet` (add `--logs` to start with the log pane open), type the password, wait for the cat, then fill the form and press Enter, then `y`. Or press Tab at the password to watch balances without unlocking.
- Point the wallet at the same URL as with `chibi node`; it keeps working while the TUI runs.

## Driving it with verify-chibi scripts

Preconditions:

- `launch.sh` does not apply: it starts a plain `chibi node`. Drive the TUI in tmux from a scratch HOME instead: `S=$(mktemp -d /tmp/chibi-tui.XXXX); mkdir -p "$S/evidence" "$S/ks"`, `E="env -u CHIBI_CONFIG -u NO_COLOR COLORTERM=truecolor HOME=$S XDG_CONFIG_HOME=$S/.config XDG_DATA_HOME=$S/.local/share"`, and `B=$PWD/target/release/chibi` after `cargo build --release -p chibi`.
- A free scratch port, for example 8750: `lsof -nP -iTCP:8750 -sTCP:LISTEN` prints nothing. Never use 8545 or 8546, and never the user's keystore.
- A scratch keystore: `cast wallet new "$S/ks" --unsafe-password hunter2` (unfunded; enough for every sub-feature but `tui-send`). For `tui-send`, a funded Sepolia key in `CHIBI_VERIFY_KEY` imported as `cast wallet import funded --private-key "$CHIBI_VERIFY_KEY" --unsafe-password hunter2 --keystore-dir "$S/ks"`; without it report `tui-send` as skipped for that reason. `KS` is the keystore file in `$S/ks`.
- `tmux`, `cast`, and outbound Sepolia access as in the [baseline](./README.md#baseline-preconditions).

- **Flags.** `$E $B wallet --rpc-port 8750 --keystore "$S/ks/missing"` exits non-zero with `cannot read the keystore $S/ks/missing` and opens no port. `$E $B wallet -b`, `$E $B node --logs`, and `$E $B run` exit 2 with a usage error. `$E $B init --network sepolia --rpc-host 127.0.0.1 --rpc-port 8750 --keystore "$KS" </dev/null` writes `keystore = "<KS>"` into `$S/.config/chibi/config.toml`, so later runs need no `--keystore`. A config with `keystore = "rel.json"` fails with `keystore rel.json is not an absolute path`.
- **Setup.** Use a second scratch HOME with no config, so nothing names a keystore: `T=$(mktemp -d /tmp/chibi-setup.XXXX)`, `F="env -u CHIBI_CONFIG HOME=$T XDG_CONFIG_HOME=$T/.config XDG_DATA_HOME=$T/.local/share"`. Run `tmux new-session -d -s chibi-setup -x 200 -y 40 "$F $B wallet --rpc-port 8751 --logs; echo exit=\$?; sleep 600"` (wide, so the saved path fits the footer). Type word N, Enter, then word M, Enter (each with `send-keys -l`, Enter separately). On the password screen type `short` + Enter (`a password needs at least 8 characters`), then `hunter22` + Enter and `hunter23` + Enter (`the passwords do not match; enter them again`), then `hunter22` + Enter twice. Within a few seconds the footer shows `saved the keystore for 0x... to $T/.config/chibi/keystores/0x....json` above the dozing cat, with no password prompt. `stat -c '%a %n' "$T/.config/chibi/keystores" "$T"/.config/chibi/keystores/*.json` prints `700` and `600`; `cast wallet address --keystore <that file> --password hunter22` prints the address in the header; `$T/.config/chibi/config.toml` holds `keystore = "<that file>"`. On the form at `-x 120 -y 40`, the token list still opens directly below the token row inside the box. On the form at `-x 80 -y 24` with the log pane closed, a balance too long to fit beside the address (more than 17 characters, such as `4.019083742425574983 ETH`) starts the next line at column 15, under the address, with nothing at column 5 under the `from` label; the box's last two inner rows are the footer `up/down field · Enter or left/right token · type amount (or max) and to` and `Enter review · l logs · q quit`; and the token list opens directly below the token row's last line.
- **Quit.** Press `q`; with a transfer still pending the pane first shows `a transfer is still pending; chibi's outbox rebroadcasts it on the next run. press q again to quit`, and a second `q` quits. The pane then shows `exit=0` on a normal screen (raw mode and the alternate screen restored), and `lsof -nP -iTCP:8750 -sTCP:LISTEN` prints nothing.
- **Mainnet.** Optional and slow (mainnet has no known state peers): run the TUI with `--network mainnet`; once the form opens, a valid transfer's Review says `sending on mainnet is not enabled yet` and `y` changes nothing.
- **Proof.** Before quitting each stage, `tmux capture-pane -p -t chibi-tui > "$S/evidence/<stage>.txt"`, with the log pane open (`l`) where the log matters. Keep the `cast` outputs next to them. Never capture the password, the private key, or the backup screen's words; capture setup panes only on the menu, confirmation, password, and saved screens.
- **Cleanup.** `tmux kill-session -t chibi-tui`, `tmux kill-session -t chibi-setup`, and `tmux kill-session -t chibi-watch`, then remove `$S` except `$S/evidence`, and all of `$T` and `$W`.

## Gotchas

- There is no `chibi.log`: under `chibi wallet` the log goes to an in-memory buffer of the last 1000 lines, shown only in the log pane, and it is gone when the TUI exits. Capture the pane with the log pane open for node proof.
- Decrypting a `cast` keystore takes a second or two (scrypt); the prompt shows `unlocking...` meanwhile.
- `Paused` appears only when every state peer drops after serving, which cannot be forced reliably on Sepolia; report `tui-paused` as observed or as not driven, never as verified from unit tests.
- The fee row and `max` for ETH need a finished estimate; Enter before it shows `waiting for the fee estimate`.
- `amount` accepts only digits, `.`, and the letters of `max`, so there `q` and `l` act as keys; the `to` field takes every printable character, so there `q` and `l` type and only Ctrl-C quits.
- A transfer left pending stays in the scratch data directory's outbox; a later `chibi node` or `chibi wallet` on the same data directory broadcasts it again.
- `tmux send-keys` reads an argument that starts with `0x` as a hex key code, not as text, so `send-keys -t chibi-tui 0xabc...` types the wrong thing. Type addresses with `send-keys -l` (literal), and send Enter in a separate `send-keys` call.
- The password is at most 256 bytes; longer input is ignored.
- The setup screens take every printable key as typing, so `q` and `l` type rather than quit or open the log pane; Esc goes back to the menu and Esc on the menu quits.
- The words stay on the backup screen only until the next key; capture them before pressing Enter.
- Some frames differ only in colour, such as the form cat's blink (eye pixels turn from dark to orange under the same `▀`). A plain `capture-pane -p` cannot see that; compare `capture-pane -p -e` captures, which keep the colour escapes.
