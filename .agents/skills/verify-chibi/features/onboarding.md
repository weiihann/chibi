# Onboarding

The shortest path: a new user installs chibi with `curl -fsSL https://raw.githubusercontent.com/weiihann/chibi/main/install.sh | sh`, optionally runs `chibi init` (network, watch-only addresses, whether to keep account history, RPC host and port), runs `chibi node`, and adds the URL to the wallet. `chibi node` also works with no config, learning the keys the wallet reads, so nothing has to be chosen. `install.sh` only downloads the prebuilt release for this OS and CPU, checks its SHA-256, installs the `chibi` binary, and prints the next steps; it runs neither `chibi init` nor `chibi`. `chibi init` writes the config and says how to start. It asks no token question: every registry token is pinned for each watched address. The user then starts chibi in the foreground or in the background, checks it, and stops it.

## Sub-features

- `onboard-install` downloads `chibi-<target>.tar.gz` and its `.sha256` from the latest GitHub release (or `CHIBI_VERSION`'s, or `CHIBI_RELEASE_URL`), prints `Checksum OK (<sha256>)`, installs `chibi` into `CHIBI_INSTALL_DIR` (default `~/.local/bin`), prints `Installed chibi <version> to <dir>/chibi`, a PATH hint when the directory is not on `PATH`, and the next steps (`chibi init`, `chibi node`, `chibi wallet`). It prompts for nothing, writes no config, and starts nothing. A hash that does not match fails with `checksum mismatch` and `Nothing was installed.`, leaving any installed binary as it was. It needs `curl` and `sha256sum` or `shasum`.
- `onboard-init-menu` asks through terminal menus: a network list, an address loop (empty line finishes, an empty first line pins no address, invalid input re-asks), `Keep a transaction history for watched accounts?` (default no), the RPC host (IP or domain) and port with defaults. No token question, and the written config has no `tokens` key.
- `onboard-init-plain` asks the same questions as plain line prompts when stdin is not a terminal; Enter takes each default.
- `onboard-init-flags` writes the config from `--network`, `--address`, `--history` or `--no-history`, `--rpc-host`, `--rpc-port`, `--beacon-url`, `--data-dir`, `--keystore`, and the peer flags (`--trusted-peer`, `--trusted-only`, `--boot-node`, `--max-outbound-peers`, `--max-inbound-peers`, `--discovery-port`, `--disable-discovery`), and asks only for what the flags leave out. There is no token flag. Overwriting a config keeps its `[[contracts]]` and `data_dir`, and says so. A config with a `tokens` line fails to load, naming the fix.
- `onboard-init-reset` writing a config deletes the chosen network's saved snapshot, pending transactions, and learned keys from `chibi.db` once the config is written, keeps remembered peers, the checkpoint, `devp2p.key`, and the account history (the message names only the first three), and prints what it deleted; it refuses, writing nothing, while a chibi runs on that data dir.
- `onboard-background` runs chibi with `chibi node -b`, reports it with `chibi status`, and stops it with `chibi stop`.
- `onboard-no-config` runs chibi with no config file at the default path: `node`, `node -b`, `status`, and `stop` use Sepolia, `127.0.0.1:8545`, no pinned keys, and the default data dir, and the run logs that no config was found and where `chibi init` would write one. A config file that exists but does not parse is still an error, and so is a `--config` or `CHIBI_CONFIG` path with no file, named in the error.

## How to get to it (user POV)

- Run `curl -fsSL https://raw.githubusercontent.com/weiihann/chibi/main/install.sh | sh`, then `chibi node` without `chibi init`, and add the logged URL to the wallet.
- Run `chibi init` directly, with or without flags.
- Run `chibi node -b`, `chibi status`, and `chibi stop`.

## Driving it with verify-chibi scripts

Preconditions:

- A scratch HOME under the [scratch root](./README.md#baseline-preconditions): `S=$(mktemp -d "$ROOT/onboard.XXXX"); mkdir -p "$S/evidence" "$S/rel" "$S/pkg"`. `E="env -u CHIBI_CONFIG HOME=$S XDG_CONFIG_HOME=$S/.config XDG_DATA_HOME=$S/.local/share"`.
- A local release, so the installer runs without a GitHub release: from the repo root, `cargo build --release --locked -p chibi`, then `T=x86_64-unknown-linux-gnu` (the target `install.sh` picks for this machine; `aarch64-apple-darwin` on Apple silicon), `cp target/release/chibi LICENSE-MIT LICENSE-APACHE "$S/pkg/"` (the binary is under `$CARGO_TARGET_DIR/release/` when that is set), `tar -czf "$S/rel/chibi-$T.tar.gz" -C "$S/pkg" chibi LICENSE-MIT LICENSE-APACHE`, and `(cd "$S/rel" && sha256sum "chibi-$T.tar.gz" > "chibi-$T.tar.gz.sha256")` (`shasum -a 256` on macOS).
- `curl` on `PATH`; `install.sh` exits with `this script needs curl` without it.
- A free port for the run, for example 8747: `lsof -nP -iTCP:8747 -sTCP:LISTEN` prints nothing.

- **Install.** From the repo root run `$E CHIBI_RELEASE_URL="file://$S/rel" CHIBI_INSTALL_DIR="$S/bin" sh install.sh </dev/null 2>&1 | tee "$S/evidence/install.txt"`. Exit code 0; the output shows `Downloading file://...`, `Checksum OK (<the sha256 in the .sha256 file>)`, `Installed chibi <version> to $S/bin/chibi`, `$S/bin is not on your PATH` with an `export PATH=` line, and `Next steps:` naming `chibi init`, `chibi node`, and `chibi wallet`. No prompt appears, `$S/.config` does not exist, and no chibi process starts. This is the same script a user pipes from `curl`; only the download URL differs.
- **Checksum mismatch.** Copy the tarball into `$S/bad/` with a `.sha256` of 64 zeros (`printf '%064d  chibi-%s.tar.gz\n' 0 "$T" > "$S/bad/chibi-$T.tar.gz.sha256"`) and run the install again with `CHIBI_RELEASE_URL="file://$S/bad"`. Exit code 1 with `error: checksum mismatch for chibi-$T.tar.gz`, the expected and actual hashes, and `Nothing was installed.`; `sha256sum "$S/bin/chibi"` is unchanged.
- **Network.** Run `tmux new-session -d -s chibi-onboard -x 160 -y 40 "$E $S/bin/chibi init; echo exit=\$?; sleep 600"` and poll `tmux capture-pane -p -t chibi-onboard` until it shows `? Network`. Do not pipe it through `tee`: with its output on a pipe, init falls back to the plain prompts. Run `tmux send-keys -t chibi-onboard Enter`. The pane shows `? Network sepolia` and `? Watch-only address`.
- **Addresses.** Run `tmux send-keys -t chibi-onboard 'not-an-address' Enter`; the pane shows `"not-an-address" is not an address`. Clear the line with 14 `BSpace` keys, then `tmux send-keys -t chibi-onboard -l '0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6'`, `tmux send-keys -t chibi-onboard Enter`, and `tmux send-keys -t chibi-onboard Enter`. The pane shows `? Keep a transaction history for watched accounts? (y/N)` next; no token question appears.
- **RPC host and port.** Run `tmux send-keys -t chibi-onboard Enter` to keep no history; the pane shows `? RPC host (127.0.0.1)`. Run `tmux send-keys -t chibi-onboard 'bad_host!' Enter`; the pane shows `is not an IP address or host name`. Clear it with 9 `BSpace` keys, then `tmux send-keys -t chibi-onboard Enter` (host `127.0.0.1`) and `tmux send-keys -t chibi-onboard '8747' Enter`. The pane shows `wrote ... (sepolia, 1 address)` with no `pinning`, the wallet URL `http://127.0.0.1:8747` with chain id `11155111`, `chibi node` / `chibi node -b` as next steps, and `exit=0`.
- **Config on disk.** Run `cat "$S/.config/chibi/config.toml"`. It has `rpc_host = "127.0.0.1"`, `rpc_port = 8747`, the checksummed address, and the default `cors_origins` and `allowed_hosts`, and no `tokens` line.
- **Background run.** Run `$E "$S/bin/chibi" node -b`. It prints `chibi is running in the background (pid <N>)`, the log path under the data dir, and `JSON-RPC: http://127.0.0.1:8747 (chain id 11155111), served once the first head is verified`. Until then `$E "$S/bin/chibi" status` prints `running (pid <N>), starting; JSON-RPC is served once the first head is verified` and `no snapshot for sepolia yet`. A second `node -b` is refused with `` chibi is already running on sepolia (pid <N>); stop it with `chibi stop` ``.
- **Serving.** Wait until `"$S/.local/share/chibi/sepolia/chibi.log"` contains `JSON-RPC on http://127.0.0.1:8747` (seconds to minutes, while it waits for a state peer (snap); the log shows a small cat and `found a state peer` once one connects). Then `CHIBI=http://127.0.0.1:8747 TOKENS="0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238 0xaA8E23Fb1079EA71e0a56F48a2aA51851D8433D0 0xfFf9976782d46CC05630D1f6eBAb18b2324d6B14" scripts/oracle-check.sh 0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6 | tee "$S/evidence/oracle-check.txt"` reports `0 difference(s)`.
- **Status and stop.** Run `$E "$S/bin/chibi" status`; it shows `running (pid <N>), JSON-RPC http://127.0.0.1:8747`, `sepolia head <N> (saved <age> ago, not re-verified)`, and one line per address with its primary ENS name when it has one, its ETH balance, and every registry token it holds a nonzero balance of (every registry token is pinned for the watched address; zero balances are omitted). Run `$E "$S/bin/chibi" stop`; it prints `stopping chibi (pid <N>)...` and `stopped`, the log contains `shutting down on SIGTERM` (helios lines such as `helios::consensus: shutting down consensus client` may follow it), and `status` then prints `not running` above the saved snapshot.
- **Flags.** Run `$E "$S/bin/chibi" init --config "$S/flags.toml" --network sepolia --address 0xe1f0ba7cf9175f61ad1fe29ee4f30249871bfc29 --no-history --rpc-host localhost --rpc-port 8545 --beacon-url https://beacon.sepolia.ethpandaops.io/nimbus --max-inbound-peers 10 --data-dir "$S/flags-data" </dev/null`. Exit code 0, no prompts, and `$S/flags.toml` has `rpc_host = "localhost"`, `beacon_url = "https://beacon.sepolia.ethpandaops.io/nimbus"`, `max_inbound_peers = 10`, `data_dir = "$S/flags-data"`, and no `tokens` line. Without `--no-history` the same command prints `Keep a transaction history for watched accounts? [y/N]` and takes the default. The separate `--data-dir` matters: init resets the chosen network's data dir and refuses while the **Background run** chibi holds the default one. `$E "$S/bin/chibi" init --help` lists `--keystore`, `--history` and `--no-history`, and no token flag. `$E "$S/bin/chibi" init --config "$S/to.toml" --network sepolia --trusted-only </dev/null` takes the defaults for the questions the flags leave out, then exits non-zero with `trusted_only = true needs at least one trusted_peers entry to connect to` and writes no `$S/to.toml`.
- **A tokens line fails.** Run `echo 'tokens = ["DAI"]' >> "$S/flags.toml"`, then `$E "$S/bin/chibi" --config "$S/flags.toml" status`. It exits non-zero with `` `tokens` was removed: every registry token is now kept for watched addresses; delete the `tokens` line or rerun `chibi init` ``.
- **Reset on rewrite.** With the background chibi from **Background run** stopped and its snapshot saved, run `echo y | $E "$S/bin/chibi" init --network sepolia --address 0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6 --rpc-host 127.0.0.1 --rpc-port 8747`. After the `Overwrite it? [y/N]` and `Keep a transaction history for watched accounts? [y/N]` prompts it prints `reset the saved sepolia state in $S/.local/share/chibi/sepolia/chibi.db: deleted 1 snapshot, ...` and then `wrote ...`; `status` then prints `no snapshot for sepolia yet`, and `devp2p.key` and `checkpoint` are still in the data dir. Start `node -b` again and rerun the same init with `echo y |`: it exits non-zero with `chibi is running on ... (pid <N>); stop it before rerunning chibi init. Nothing was written`. Without the `y`, init keeps the existing config (`Overwrite it?` defaults to no) and never reaches that check. Stop it again.
- **Plain prompts.** In a second scratch HOME (`P=$(mktemp -d "$ROOT/plain.XXXX")`, and `$EP` as `$E` with `$P` in place of `$S`), run `printf '\n0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6\n\n\n\n8748\n' | $EP "$S/bin/chibi" init 2>&1 | tee "$S/evidence/init-plain.txt"`: the lines answer the network, the address, the end of the address list, history, the host, and the port. The output shows the plain prompts (`Network [sepolia]:`, `Watch-only address (blank to finish):`, `Keep a transaction history for watched accounts? [y/N]`, `RPC host, an IP address or domain [127.0.0.1]:`, `RPC port [8545]:`), `wrote ... (sepolia, 1 address)`, and the wallet URL `http://127.0.0.1:8748`; this is the `onboard-init-plain` path. One blank line fewer sends `8748` to the host prompt (`"8748" is not an IP address or host name`) and leaves the port at 8545. Then `printf '\n\n\n\n\n' | $EP "$S/bin/chibi" init --config "$P/none.toml"` prints `wrote ... (sepolia, 0 addresses)`: no address is required. Remove `$P` afterwards.
- **No config.** Never use port 8545 here: it is the user's chibi and wallet port. In a third scratch HOME (`N=$(mktemp -d "$ROOT/noconf.XXXX")`, and `$EN` as `$E` with `$N` in place of `$S`), run `$EN "$S/bin/chibi" node -b --rpc-port 8749` without `chibi init`. It prints the pid, the log path `$N/.local/share/chibi/sepolia/chibi.log`, and `JSON-RPC: http://127.0.0.1:8749 (chain id 11155111), served once the first head is verified`. The log contains `no config at $N/.config/chibi/config.toml; using the defaults` and the `starting` line with `network=sepolia watched=0`. Wait for `JSON-RPC on http://127.0.0.1:8749, chain id 11155111`; then `cast balance 0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6 --rpc-url http://127.0.0.1:8749` returns a balance, as a wallet's first read would. `$EN "$S/bin/chibi" status` prints the running line with `http://127.0.0.1:8749`, and `$EN "$S/bin/chibi" stop` stops it. `$N/.config/chibi/config.toml` still does not exist. Then `mkdir -p "$N/.config/chibi" && echo 'network = "goerli"' > "$N/.config/chibi/config.toml"` and `$EN "$S/bin/chibi" node` exits non-zero with `invalid config`. Copy the log into `$S/evidence/no-config.log` and remove `$N`.
- **Proof.** Run `tmux capture-pane -p -S - -t chibi-onboard > "$S/evidence/pane.txt"` and copy the config files and the node log into `$S/evidence/`.
- **Cleanup.** Run `$E "$S/bin/chibi" stop` if it still runs, `tmux kill-session -t chibi-onboard`, then remove `$S` except `$S/evidence`.

## Gotchas

- The menus need a real terminal. Piping into `chibi init` gives the plain prompts instead (`Network [sepolia]:`, `RPC host, an IP address or domain [127.0.0.1]:`, and so on), which is the `onboard-init-plain` path, not `onboard-init-menu`.
- `chibi init` asks for whatever its flags leave out; with stdin at `/dev/null`, each of those plain prompts takes its default. Pass `--network`, `--address`, `--history` or `--no-history`, `--rpc-host`, and `--rpc-port` for a run with no prompts.
- In the address prompt, a rejected line stays in the input box. Clear it with `BSpace` before typing the next address.
- The config lives under `$XDG_CONFIG_HOME/chibi/` and the data under `$XDG_DATA_HOME/chibi/` on macOS and Linux alike; with those unset, under `$HOME/.config` and `$HOME/.local/share`. `CHIBI_CONFIG` overrides the config path, so it must be unset. Override HOME and both XDG variables and unset `CHIBI_CONFIG` to isolate a run.
- `install.sh` without `CHIBI_INSTALL_DIR` writes `~/.local/bin/chibi` under the scratch HOME only if HOME is overridden; always set `CHIBI_INSTALL_DIR` so the user's binary is never replaced.
- `chibi status` shows the URL the running chibi serves, including `--rpc-host` and `--rpc-port` overrides, only once the first head is verified (`starting` before that); with no chibi running it shows only the saved snapshot.
- `chibi node -b`, `chibi stop`, and `chibi status` find the node through the config's data dir, or the default one without a config. Pass the same `--network`, `--data-dir`, and `--config` (or `CHIBI_CONFIG`) to all three commands.
- The state-peer wait varies from seconds to several minutes, and a state peer can drop right after serving; a read then fails with `no connected peer serves state (snap)` until another connects. Retry after the next `status head=` line shows `state_peers=1` or more.
