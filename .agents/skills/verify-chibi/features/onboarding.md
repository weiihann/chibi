# Onboarding

The shortest path: a new user installs chibi, runs `chibi init` (network, watch-only addresses, RPC host and port), runs `chibi node`, and adds the URL to the wallet. `chibi node` also works with no config, learning the keys the wallet reads, so nothing has to be chosen. `./install.sh` installs the `chibi` binary and runs `chibi init`, which writes the config and says how to start. It asks no token question: every registry token is pinned for each watched address. The user then starts chibi in the foreground or in the background, checks it, and stops it.

## Sub-features

- `onboard-install` builds and installs the binary with cargo, runs init on a terminal, and does not start chibi.
- `onboard-init-menu` asks through terminal menus: a network list, an address loop (empty line finishes, an empty first line pins no address, invalid input re-asks), the RPC host (IP or domain) and port with defaults. No token question, and the written config has no `tokens` key.
- `onboard-init-plain` asks the same questions as plain line prompts when stdin is not a terminal; Enter takes each default.
- `onboard-init-flags` writes the config from `--network`, `--address`, `--rpc-host`, `--rpc-port`, `--beacon-url`, `--data-dir`, and the peer flags (`--trusted-peer`, `--trusted-only`, `--boot-node`, `--max-outbound-peers`, `--max-inbound-peers`, `--discovery-port`, `--disable-discovery`) without prompting. There is no token flag. Overwriting a config keeps its `[[contracts]]` and `data_dir`, and says so. A config with a `tokens` line fails to load, naming the fix.
- `onboard-init-reset` writing a config deletes the chosen network's saved snapshot, pending transactions, and learned keys from `chibi.db` once the config is written, keeps remembered peers, the checkpoint, and `devp2p.key`, and prints what it deleted; it refuses, writing nothing, while a chibi runs on that data dir.
- `onboard-background` runs chibi with `chibi node -b`, reports it with `chibi status`, and stops it with `chibi stop`.
- `onboard-no-config` runs chibi with no config file at the default path: `node`, `node -b`, `status`, and `stop` use Sepolia, `127.0.0.1:8545`, no pinned keys, and the default data dir, and the run logs that no config was found and where `chibi init` would write one. A config file that exists but does not parse is still an error, and so is a `--config` or `CHIBI_CONFIG` path with no file, named in the error.

## How to get to it (user POV)

- Install, then `chibi node` without `chibi init`, and add the logged URL to the wallet.
- Run `./install.sh` in a terminal from the repo root.
- Run `chibi init` directly, with or without flags.
- Run `chibi node -b`, `chibi status`, and `chibi stop`.

## Driving it with verify-chibi scripts

Preconditions:

- A scratch HOME: `S=$(mktemp -d /tmp/chibi-onboard.XXXX); mkdir -p "$S/evidence"`. `E="env -u CHIBI_CONFIG HOME=$S XDG_CONFIG_HOME=$S/.config XDG_DATA_HOME=$S/.local/share"`.
- A free port for the run, for example 8747: `lsof -nP -iTCP:8747 -sTCP:LISTEN` prints nothing.

- **Install.** Run `tmux new-session -d -s chibi-onboard -x 160 -y 40 "$E RUSTUP_HOME=$HOME/.rustup CARGO_HOME=$HOME/.cargo CARGO_INSTALL_ROOT=$S/install CARGO_TARGET_DIR=$PWD/target ./install.sh; sleep 600"`. Do not pipe it through `tee`: with its output on a pipe, init falls back to the plain prompts. Poll `tmux capture-pane -p -t chibi-onboard` until it shows `? Network`; the **Proof** step saves the pane as the install evidence.
- **Network.** Run `tmux send-keys -t chibi-onboard Enter`. The pane shows `? Network sepolia` and `? Watch-only address`.
- **Addresses.** Run `tmux send-keys -t chibi-onboard 'not-an-address' Enter`; the pane shows `"not-an-address" is not an address`. Clear the line with 14 `BSpace` keys, then `tmux send-keys -t chibi-onboard '0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6' Enter` and `tmux send-keys -t chibi-onboard Enter`. The pane shows `? RPC host` next; no token question appears.
- **RPC host and port.** Run `tmux send-keys -t chibi-onboard 'bad_host!' Enter`; the pane shows `is not an IP address or host name`. Clear it with 9 `BSpace` keys, then `tmux send-keys -t chibi-onboard Enter` (host `127.0.0.1`) and `tmux send-keys -t chibi-onboard '8747' Enter`. The pane shows `wrote ... (sepolia, 1 address)` with no `pinning`, the wallet URL `http://127.0.0.1:8747` with chain id `11155111`, and `chibi node` / `chibi node -b` as next steps. No `light client` line follows: install does not start chibi.
- **Config on disk.** Run `cat "$S/.config/chibi/config.toml"`. It has `rpc_host = "127.0.0.1"`, `rpc_port = 8747`, the checksummed address, and the default `cors_origins` and `allowed_hosts`, and no `tokens` line.
- **Background run.** Run `$E "$S/install/bin/chibi" node -b`. It prints the pid, the log path under the data dir, and the RPC URL. `$E "$S/install/bin/chibi" status` prints `running (pid <N>), JSON-RPC http://127.0.0.1:8747`. A second `node -b` is refused with the same pid.
- **Serving.** Wait until `"$S/.local/share/chibi/sepolia/chibi.log"` contains `JSON-RPC on http://127.0.0.1:8747` (minutes, while it waits for a state peer (snap); the log shows a small cat and `found a state peer` once one connects). Then `CHIBI=http://127.0.0.1:8747 TOKENS="0x1c7D4B196Cb0C7B01d743Fbc6116a902379C7238 0xaA8E23Fb1079EA71e0a56F48a2aA51851D8433D0 0xfFf9976782d46CC05630D1f6eBAb18b2324d6B14" scripts/oracle-check.sh 0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6 | tee "$S/evidence/oracle-check.txt"` reports `0 difference(s)`.
- **Status and stop.** Run `$E "$S/install/bin/chibi" status`; it shows the running line and one line per address with its ETH balance and every registry token it holds a nonzero balance of (every registry token is pinned for the watched address; zero balances are omitted). Run `$E "$S/install/bin/chibi" stop`; it reports the process stopped, the log contains `shutting down on SIGTERM` (helios lines such as `helios::consensus: shutting down consensus client` may follow it), and `status` then prints `not running` above the saved snapshot.
- **Flags.** Run `$E "$S/install/bin/chibi" init --config "$S/flags.toml" --network sepolia --address 0xe1f0ba7cf9175f61ad1fe29ee4f30249871bfc29 --rpc-host localhost --rpc-port 8545 --beacon-url https://beacon.sepolia.ethpandaops.io/nimbus --max-inbound-peers 10 --data-dir "$S/flags-data" </dev/null`. Exit code 0, no prompts, and `$S/flags.toml` has `rpc_host = "localhost"`, `beacon_url = "https://beacon.sepolia.ethpandaops.io/nimbus"`, `max_inbound_peers = 10`, `data_dir = "$S/flags-data"`, and no `tokens` line. The separate `--data-dir` matters: init resets the chosen network's data dir and refuses while the **Background run** chibi holds the default one. `$E "$S/install/bin/chibi" init --help` lists no token flag. `--trusted-only` alone exits non-zero with `trusted_only = true needs at least one trusted_peers entry to connect to`.
- **A tokens line fails.** Run `echo 'tokens = ["DAI"]' >> "$S/flags.toml"`, then `$E "$S/install/bin/chibi" --config "$S/flags.toml" status`. It exits non-zero with `` `tokens` was removed: every registry token is now kept for watched addresses; delete the `tokens` line or rerun `chibi init` ``.
- **Reset on rewrite.** With the background chibi from **Background run** stopped and its snapshot saved, run `echo y | $E "$S/install/bin/chibi" init --network sepolia --address 0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6 --rpc-host 127.0.0.1 --rpc-port 8747`. After the `Overwrite it? [y/N]` prompt it prints `reset the saved sepolia state in $S/.local/share/chibi/sepolia/chibi.db: deleted 1 snapshot, ...` and then `wrote ...`; `status` then prints `no snapshot for sepolia yet`, and `devp2p.key` and `checkpoint` are still in the data dir. Start `node -b` again and rerun the same init: it exits non-zero with `chibi is running on ... (pid <N>); stop it before rerunning chibi init. Nothing was written`.
- **Plain prompts.** In a second scratch HOME (`P=$(mktemp -d /tmp/chibi-plain.XXXX)`, and `$EP` as `$E` with `$P` in place of `$S`), run `printf '\n0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6\n\n\n8748\n' | $EP "$S/install/bin/chibi" init 2>&1 | tee "$S/evidence/init-plain.txt"`. The output shows the plain prompts (`Network [sepolia]:`, `RPC host, an IP address or domain [127.0.0.1]:`) and `wrote ... (sepolia, 1 address)`; this is the `onboard-init-plain` path. Then `printf '\n\n\n\n' | $EP "$S/install/bin/chibi" init --config "$P/none.toml"` prints `wrote ... (sepolia, 0 addresses)`: no address is required. Piping into `install.sh` instead skips init and prints `Input is not a terminal, so chibi init was not run`. Remove `$P` afterwards.
- **No config.** Never use port 8545 here: it is the user's chibi and wallet port. In a third scratch HOME (`N=$(mktemp -d /tmp/chibi-noconf.XXXX)`, and `$EN` as `$E` with `$N` in place of `$S`), run `$EN "$S/install/bin/chibi" node -b --rpc-port 8749` without `chibi init`. It prints the pid, the log path `$N/.local/share/chibi/sepolia/chibi.log`, and `JSON-RPC: http://127.0.0.1:8749 (chain id 11155111)`. The log contains `no config at $N/.config/chibi/config.toml; using the defaults` and the `starting` line with `network=sepolia watched=0`. Wait for `JSON-RPC on http://127.0.0.1:8749, chain id 11155111`; then `cast balance 0x3d767bf85779e2b550ab5fcd7e3be39fb77a5ce6 --rpc-url http://127.0.0.1:8749` returns a balance, as a wallet's first read would. `$EN "$S/install/bin/chibi" status` prints the running line with `http://127.0.0.1:8749`, and `$EN "$S/install/bin/chibi" stop` stops it. `$N/.config/chibi/config.toml` still does not exist. Then `mkdir -p "$N/.config/chibi" && echo 'network = "goerli"' > "$N/.config/chibi/config.toml"` and `$EN "$S/install/bin/chibi" node` exits non-zero with `invalid config`. Copy the log into `$S/evidence/no-config.log` and remove `$N`.
- **Proof.** Run `tmux capture-pane -p -S - -t chibi-onboard > "$S/evidence/pane.txt"` and copy the config files and the node log into `$S/evidence/`.
- **Cleanup.** Run `$E "$S/install/bin/chibi" stop` if it still runs, `tmux kill-session -t chibi-onboard`, then remove `$S` except `$S/evidence`.

## Gotchas

- The menus need a real terminal. Piping into `chibi init` gives the plain prompts instead (`Network [sepolia]:`, `RPC host, an IP address or domain [127.0.0.1]:`, and so on), which is the `onboard-init-plain` path, not `onboard-init-menu`. Piping into `install.sh` skips `chibi init` altogether.
- In the address prompt, a rejected line stays in the input box. Clear it with `BSpace` before typing the next address.
- The config lives under `$XDG_CONFIG_HOME/chibi/` and the data under `$XDG_DATA_HOME/chibi/` on macOS and Linux alike; with those unset, under `$HOME/.config` and `$HOME/.local/share`. `CHIBI_CONFIG` overrides the config path, so it must be unset. Override HOME and both XDG variables and unset `CHIBI_CONFIG` to isolate a run.
- Overriding HOME without `RUSTUP_HOME` and `CARGO_HOME` makes cargo look for a toolchain in the scratch directory and fail.
- `chibi status` shows the URL the running chibi serves, including `--rpc-host` and `--rpc-port` overrides; with no chibi running it shows only the saved snapshot.
- `chibi node -b`, `chibi stop`, and `chibi status` find the node through the config's data dir, or the default one without a config. Pass the same `--network`, `--data-dir`, and `--config` (or `CHIBI_CONFIG`) to all three commands.
